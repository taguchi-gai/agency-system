# 設計方針メモ：支払方法（現金・請求書払い）の追加（2026-09-22）

本部回答③を受けて確定した運用を、DB設計（`docs/04_データベース設計.md`）と本番アプリに落とすための方針。
モックへの反映は別途判断（本部は開発環境で確認する前提のため、DB設計を優先）。

## 1. 支払方法と選択フロー（取次店の申込画面）

```
顧客区分を選ぶ：個人 ／ 法人
  ├ 個人： カード ／ PayPay ／ 現金
  └ 法人： カード ／ PayPay ／ 現金 ／ 請求書払い（月末締め・銀行振込）
```
- カード／PayPay → 決済代行会社（SBペイメントサービス）の画面へ。取引IDだけを受け取る（カード情報非保持）。
- 現金 → 決済画面に飛ばさず取次を完了。注文は「未決済・現金（施工時回収）」。
- 請求書払い → 法人名・部署・担当者・請求先住所を必須入力。取次を完了し、注文は「未決済・請求書払い」。
  本部の事前承認を挟むかは本部確認中（追加確認2）。

## 2. お金の流れ

| 手段 | 回収する人 | 決済手数料 | 配分の基礎 | 本部の入金 | 取次店10% | 施工代理店80% |
|---|---|---|---|---|---|---|
| カード／PayPay | 決済代行会社 | あり（手段別料率） | 売上−手数料 | 代行会社から入金 | 本部が振込 | 本部が振込 |
| 現金 | **施工代理店（施工時）** | なし | 売上 | **施工代理店が20%を振込**（手数料は施工代理店負担） | 本部が振込 | 施工代理店が手元に残す |
| 請求書払い | 本部（法人へ請求） | なし | 売上 | 法人から振込 | 本部が振込 | 本部が振込 |

- 配分の計算式・端数処理は変えない（`売上−手数料` を基礎に 10/10/80、取次店・施工代理店を先に確定し残りを本部）。
  現金・請求書払いは料率テーブルに **0%** の行として持つだけで、計算ロジックは共通。
- 支払対象は施工完了の案件のみ・締めは完了日の月（変更なし）。請求書払いは入金前でも完了月の配分対象にする
  （未回収リスクは本部が負う。ここも本部に念押し）。

## 3. 施工代理店からの現金分20%の回収

- **本部→施工代理店の請求書**（種別 `cash_collection`）を月次で自動作成。明細＝その月に施工完了した現金案件の
  `売上×20%` を案件ごとに1行（取次店分10%を含むことを備考に明記）。
- 既存の請求書の状態（作成済み→送付済み→入金済）と採番（INV-年月-連番）をそのまま使う。
- カード分80%の支払と相殺して1本にするかは本部確認中（追加確認4）。設計上は「請求書」と「支払」を別テーブルで持ち、
  相殺する場合は精算時に両方を参照して差引額を出す（どちらの運用にも対応できる形にしておく）。

## 4. 施工代理店の完了報告ゲート

```
施工日確定 → 施工前確認済み（署名） → [現金の場合：回収完了を記録] → 施工完了
```
- 注文に `payment_method` と `cash_collected_at`（回収日時・記録者）を持つ。
- `payment_method = cash` かつ `cash_collected_at` が空なら「施工完了」ボタンを無効化し理由を表示。
- 本部の施工注文管理・案件詳細と施工代理店の施工案件に「現金決済」「回収完了／未回収」のバッジ。

## 5. 法人向け請求書払い

- 本部→法人顧客の請求書（種別 `customer_invoice`）。宛先は注文に入力された法人情報。
- **月末締めで月内の案件をまとめて1枚（2026-09-23 利用者確定）**。締めは施工完了日の月。同じ法人から月内に複数件あっても1枚。
  モックでは本部メニュー「顧客請求」に実装済み。本番では法人名ではなく顧客マスタのIDで束ねる。
- 支払期日の既定・振込手数料の負担文言は設定値にし、本部回答で切り替える（追加確認2c・3）。
- 入金消込：作成済み→送付済み→入金済 に「期日超過」の表示を加える（状態を増やさず、期日と入金日から判定）。

## 8. 複数台の申し込み（申込 1 : 施工案件 N）— 2026-09-23 着手予定

### 画面（取次店の申込フォーム）
- 消耗品注文と同じ「明細行」形式にする：**車種／自動判定された区分／やにとり／台数**を1行とし、「車種を追加」で行を増やす。
- 各行に**車両番号（ナンバー下4桁など）を任意入力**。同一車種を複数台頼まれたときの識別と、施工前確認の署名の紐づけに使う。
  台数分の入力欄を出す（例：2台なら番号欄が2つ）。未入力でも申し込める。
- 金額は全行の合計を表示し、決済は**申込単位で1回**。
- 希望日・希望時間・お客さま情報・支払方法・請求先は**申込単位**（1組だけ入力する）。

### データ構造
```
申込 application … 顧客・請求先・支払方法・決済1回・希望日/時間・取次店
  └ 施工案件 service_order（車両1台につき1件）
       車種・区分・やにとり・金額・車両番号
       施工代理店・施工日・施工前確認の署名・完了報告・完了日
```
- 施工案件の番号は申込番号の枝番にする（例：AP-0012 の案件 AP-0012-1 / -2）。既存の `SO-xxxx` からの移行方針は実装時に決める。

### 割り当て・ステータス
- **施工代理店の割り当ては申込単位で1社**（同じ場所・同じ日にまとめて施工する前提）。車両ごとに分ける余地は構造に残す。
- **施工前確認の署名と完了報告は車両ごと**。申込のステータスは配下の案件から導出する（全車完了で「施工完了」）。
- **現金の回収記録は申込単位**（まとめて受け取るため）。全車の完了報告には回収記録が前提、という既存ゲートは維持。

### 金額・配分
- **決済手数料は決済1回に対して発生する**ので、申込の合計額に料率をかけて算出し、各案件に金額比で按分する。
  按分の端数は最後の案件に寄せ、`手数料の合計 = 申込の手数料` を保つ。
- 配分（10/10/80）は従来どおり案件ごとに計算してから合算。**売上と1円まで一致するルールは変えない。**
- 請求書（顧客請求・現金回収）は申込単位ではなく**案件単位の明細**で出す（1台1行）。集計の締めは従来どおり施工完了日の月。

## 9. 取次店兼施工代理店（加盟店）の配分 — 本部確定 2026-09-23 ／ **モック実装済み 2026-09-23**

> モックへの実装は完了（詳細は context.md「★2026-09-23 追記（2）」）。本番のDB設計にもこの方針をそのまま持ち込む。


- 取次店が施工代理店になった場合、**分類は施工代理店**。その店で発生した案件は取次手数料も自社が取り、**合計90%**（本部10%）。
- 一般形：**案件ごとに「取次した主体」と「施工した主体」が同一なら、両者の取り分を合算して1社に支払う。**
  自社が取り次いだ案件を他社が施工した場合は取次分10%のみ（既存の「他社取次店」と同じ扱い）。
- 実装：施工代理店が**自社の取次窓口**（QR・注文フォーム）を持てるようにし、その窓口の案件は `取次 = 施工` と判定する。
  振込は会社単位でまとめる（同じ会社への二重振込を作らない）。

### 取次機能の付与は本部のボタンで（2026-09-23 利用者確定）
- 施工代理店マスタに**「取次機能」のオン/オフ**を持たせる。本部が施工代理店管理の画面でボタンを押すと、
  その会社の**自社取次窓口（QR・注文フォーム）が自動で作られる**。取次店として別に登録する手間をなくす。
- 兼業の会社は**施工代理店としてログイン**し、その画面に注文フォームと自社QRが増える（本部回答「分類は施工代理店」に沿う）。
- オフに戻す場合、過去の案件は取次窓口の記録を保持したまま新規受付だけ止める（過去の配分を壊さないため）。

### アップセル（自社で取り次いで自社で施工する）の流れ
施工代理店にはエアコン清掃・ハウスクリーニング等の業者もおり、**その場で「車の除菌消臭も」と受注して即施工する**場面が多い想定。
- **施工希望日の「3営業日後以降」制限は自社案件では外す**（この制限は本部が施工代理店を探す猶予のためのもの。自社施工なら不要）。当日を選べるようにする。
- **自社取次窓口からの申込は、本部の割り当てを介さず自動的に自社へ割り当てる**（ステータスは「施工日確定」から開始）。
  本部の施工注文管理には記録として出るが、割り当て操作は不要。
- 結果：申込 → 決済 → その場で施工 → 施工前確認の署名 → 完了報告 まで現場で完結する。配分は取次＝施工のため自動的に90%。
- 影響：`splitOf` / `payoutRows` / 振込CSV / 施工代理店・取次店の「受取見込み」表示・月別実績。
  兼業の施工代理店の画面では、受取見込みを 80% ではなく 90% で表示する必要がある。
- DB設計への反映：取次窓口に「どの施工代理店の自社窓口か」を持たせ、配分計算は率の定数ではなく
  **案件ごとの取次主体・施工主体の比較**で決める（将来、別の兼業パターンが出ても壊れないようにする）。
