## ★2026-09-23 追記（1）：複数台の申し込み（B案）と、取次店兼施工代理店の配分90%

### 1. 取次店兼施工代理店の配分（本部確定）

取次店が施工代理店になった場合、**分類は「施工代理店」**。その店で発生した案件は取次手数料も自社で取るため、
**施工代理店80% ＋ 取次10% ＝ 90%** がその1社の取り分になる（本部10%は変わらない）。

- 配分ルールの一般形：**案件ごとに「取次した主体」と「施工した主体」が同一なら、両方の取り分を合算して1社に支払う**。
  兼業でも、自社が取り次いだ案件を他社の施工代理店が施工した場合は取次分10%のみ（既存の「他社取次店」の考え方と同じ）。
- 実装方針：施工代理店が自社の取次窓口（QR・注文フォーム）を持てるようにし、その窓口経由の案件は
  `取次 = 施工` と判定して合算する。振込は会社単位でまとめる（同じ会社に2回振り込まない）。
- **取次機能は本部が施工代理店管理の画面のボタンで付与する**（オンにすると自社取次窓口とQRが自動生成。取次店として別登録しない）。
  兼業の会社は施工代理店としてログインし、その画面に注文フォームが増える。
- **アップセル対応**：施工代理店にはエアコン清掃・ハウスクリーニング業者もおり、訪問先でその場で受注し即施工する場面が多い想定。
  自社取次窓口からの申込は **3営業日後以降の制限を外し**（本部が施工店を探す猶予が不要なため）、**自動的に自社へ割り当てて
  「施工日確定」から開始**する。申込→決済→施工→署名→完了報告が現場で完結し、本部の割り当て操作が要らない。
- 影響範囲：`splitOf`／`payoutRows`／振込CSV／施工代理店・取次店の「受取見込み」表示・月別実績。
  **1円一致のルール（取次店・施工代理店を先に確定し残りを本部）は維持する。**

### 2. 複数台の申し込みに対応（B案・利用者確定）

現在は「1申込＝1台」。取次店（中古車販売店）が在庫車をまとめて依頼する場面に合わないため、
**申込1件 : 施工案件N件**の構造に分ける。

- 申込フォームは消耗品注文と同じ形にする：**車種の明細行＋台数のプルダウン、「車種を追加」ボタン**で別車種を追加。
- **車両番号（ナンバー下4桁など）の入力欄を任意で追加**。同じ車種を複数台頼まれたときに、
  施工代理店の画面と施工前確認の署名がどの車のものか分かるようにするため。
- **希望日は申込単位**（同じ場所・同じ日にまとめて施工する前提）。施工代理店の割り当ても申込単位で1社。
  必要になれば後から車両ごとに分けられる形にしておく。
- 送信時に台数分の施工案件へ展開する。施工前確認の署名・完了報告は**車両ごと**。現金の回収記録は**申込単位**。
- **決済手数料は決済1回に対して発生する**ため、申込の合計額で計算してから各案件に按分する
  （現在は1案件ごとに計算）。配分が売上と1円まで一致するルールは維持する。
- 作業順（小刻みにコミット）：①申込フォーム（明細行＋台数＋ナンバー）→ ②案件への展開・割り当て → ③配分・請求への反映。

## ★2026-09-21 追記（5）：セキュリティ方針（本番設計の前提）

構成は **Supabase（PostgreSQL）+ Vercel** を軸に検討中。サーバー保守の担当者が社内にいないため、
OS・ミドルウェアのパッチ適用を自前で背負わないマネージド型を選ぶ、という前提を置いている。

### 1. クレジットカード情報は自社で受け取らない（最重要・法令要件）

日本では割賦販売法により、加盟店にカード番号等の適切な管理が義務付けられている。実務指針である
「クレジットカード・セキュリティガイドライン」では **カード情報の非保持化**（自社の機器・ネットワークに
カード情報を保存しない／処理しない／通過させない）が求められる。

- 決済代行会社（PSP）の **リダイレクト型** または **トークン決済（埋め込み型）** を使う。
  カード番号はお客さまのブラウザから決済代行会社へ直接送られ、こちらには取引IDやトークンだけが返る。
- この構成なら Supabase / Vercel をカード情報が通らないため、PCI DSS も最も軽い区分（SAQ A）で済む。
- **現在のモックの決済画面（`openPaymentModal`）は見た目だけのダミー。本番ではこの画面に決済処理を
  繋ぐのではなく、画面ごと決済代行会社が提供するものに置き換える。** ここを誤ると非保持化から外れる。
- 決済画面には解析タグ・広告タグを一切入れない（1つでも入れると簡易区分から外れる場合がある）。
- 決済代行会社は**ソフトバンク系（SBペイメントサービス）を想定**。本部に確認中。
  PayPay とカードを1社でまとめられるかが選定のポイント。

### 2. 改ざん・バックドア対策（サイト改ざんの主要因を構造的に排除する）

日本語キーワードハック（改ざんされたサイトに日本語のスパムページが埋め込まれ、Googleのクロールの
たびに検索結果上で増えていく）や Webシェル（サーバー上に置かれる遠隔操作用の小さなスクリプト）は、
実際に多発している。2026年8月にも WordPress の既知の脆弱性を突いて数万サイトにバックドアが
設置された事例（WP-SHELLSTORM）が報告されている。

**これらの被害はほぼすべて「サーバー上のファイルを書き換えられる構成」で起きている。**
具体的には PHP／WordPress／プラグイン／レンタルサーバーの組み合わせ。

採用予定の構成は、この攻撃経路を構造的に持たない：
- **Vercel のデプロイは書き換え不可（イミュータブル）**。動いているサーバーにファイルを書き込めないため、
  Webシェルを置く場所そのものが存在しない。
- **本番を変更する唯一の経路が Git へのコミット**。FTP も管理画面からのファイル編集も無い。
- PHP を実行しない。CMS もプラグインも使わない。

**そのうえで、この構成に残るリスクと対策：**

| リスク | 対策 |
|---|---|
| GitHubアカウントの乗っ取り → 悪意あるコミットが自動デプロイされる | GitHubに二要素認証を必須化。mainブランチを保護し、直接pushを禁止してレビューを通す |
| npmパッケージの供給網攻撃（依存ライブラリに悪意あるコードが混入） | 依存を最小限に保つ。lockfileを必ずコミット。`npm audit` を定期実行。新規パッケージ追加時は必要性を吟味 |
| 秘密情報（APIキー等）のGit混入 | 環境変数で管理し、`.env` はコミットしない。GitHubのシークレットスキャンを有効化 |
| **行レベルセキュリティ（RLS）の設定漏れ** ← この構成で最大のリスク | 後述 |

### 3. 行レベルセキュリティ（RLS）— この構成で最も注意すべき点

現在のモックは「取次店Aの画面には取次店Aのデータだけ出す」という絞り込みを**画面側のJavaScript**で
行っている（例：`serviceOrders.filter(o => o.shopId === session.entityId)`）。
本番でこれをそのまま持ち込むと、通信を直接操作された場合に他店の顧客情報が取得できてしまう。

- **必ずデータベース側（SupabaseのRLSポリシー）で強制する。** 画面側の絞り込みは利便性のためだけのもの、
  と位置づける。
- 強い権限を持つキー（service_role）はブラウザに絶対に置かない。サーバー側でのみ使う。
- 本部アカウント（全データにアクセスできる）は二要素認証を必須にする。
- 設計時に「誰がどのテーブルの何行を読めるか」の表を作り、それをRLSポリシーに落とす。

### 4. 個人情報の保護

カード情報を扱わなくても、お客さまの氏名・電話番号・住所・署名画像は個人情報にあたり、
個人情報保護法上の安全管理措置の対象になる。
- 署名画像は公開URLに置かず、権限を確認したうえで配信する（Supabase Storage のアクセスポリシー）。
- バックアップの取得と、復元できることの定期確認。
- 退職・契約終了時のアカウント無効化の手順を決めておく。

  （税抜は 15,000／18,000／20,000／5,000。2026-09-12に「今の施工料金は税抜き」と指摘を受け修正）
- **消耗品**（すべて税込）：車の消臭プロ10L 16,500円 ／ タバコの臭い取り1L 2,200円 ／
  280ml空スプレー＋280mlパウチのセット（施工代理店卸1,000円・取次店2,000円・小売2,500円）。
  セット商品は**準備が整うまで取次店・施工代理店の注文画面に出さない**（`published: false`）。
- **送料**：15,000円以上で無料、15,000円未満は1,000円。
- **配分**：売上から決済代行会社の手数料を引いた額をベースに、**本部10%／取次店10%／施工代理店80%**。
- **端数処理（2026-09-12 追加で確定）**：各取り分をそれぞれ四捨五入すると合計が売上とズレるため
  （6月売上85,800円で1円合わないと指摘あり）、**振込額になる取次店・施工代理店を先に確定させ、
  残り全額を本部の取り分とする**方式に決定。`決済手数料 + 取次店 + 施工代理店 + 本部 = 売上` が必ず一致する。
  配分は**案件ごとに計算してから合算**する（決済手数料は1件ごとに発生するため）。
- **支払対象を「施工完了」の案件のみに限定**（2026-09-12 追加確定）：キャンセル・返金の可能性があるため、
  施工中・確認中の段階では未確定として扱い、**施工完了となった案件だけ**が売上管理の「確定売上」・
  支払管理の配分対象になる。未完了分は「施工中・未完了（参考）」として別枠で表示し、支払には含めない。
  完了した月の月次バッチに自動的に反映される。案件詳細でも未完了の案件は「未確定・参考」バッジを出し、
  配分額はあくまで参考値であることを明示している。
- **計算ロジックの全画面監査（2026-09-12）**：一から再計算する検算スクリプトで、注文金額・1案件の配分・
  月次支払・施工代理店/取次店ごとの行・消耗品の送料込み金額・完了/未完了の合計を突き合わせ、すべて一致を確認。
  監査で見つけて直した点：
  1. **締め月の基準が受付日になっていた**（画面の説明は「完了した月」なのに実装は受付日ベース）。
     `completedAt`（施工完了日）を記録し、確定売上・支払は**完了日の月**、未完了（参考）は受付日の月で集計するよう修正。
     例：5/28受付・6/2完了の SO-0004 は6月分。6月に受け付けて7月に完了した案件は7月分になる。
  2. **取次店の画面に配分がまったく無かった**。取次履歴に「施工完了分の取次金額」「受取見込み額（10%）」と
     行ごとの受取見込み（未完了は「完了後に確定」表示）を追加。施工代理店の行も同じ表示に統一。
  3. 未使用ヘルパー削除、`reduce` の null ガード、本部ダッシュボードの消耗品売上に「送料込み」を明記。
  **消耗品の売上は未出荷分も含める（本部確定）**。ただし未出荷がいくらかは分けて見せる：
  売上管理・消耗品受発注管理に「出荷済／未出荷」の件数・金額を表示。

  両方に「請求書を作成」ボタン）。手動作成も可。編集画面では宛先（施工代理店／取次店）、発行日、支払期限、
  明細（**商品はマスタからプルダウン選択**・数量・単価を修正可）、送料（自動計算ボタンあり・手修正可）、備考を
  編集でき、合計・内消費税を即時計算。プレビューは印刷／PDF保存対応（印刷時は請求書だけ出る）。
  **作成入口は「消耗品受発注」画面の各注文行のみ**（請求書管理画面では作成しない。複数入口は分かりにくいとの指摘で一本化）。
  状態：**作成済み → 送付済み → 入金済**。送付済みにすると送付日（`sentAt`）を記録し、
  二重送付防止のため (1) 注文行の「請求書」欄に状態バッジ＋番号＋送付日を表示、(2) プレビューに「◯日に送付済み・再送注意」の警告、
