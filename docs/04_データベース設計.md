## 1. 前提と方針

### 1.1 技術構成

| 層 | 採用 | 備考 |
|---|---|---|
| データベース | Supabase（PostgreSQL 15 以降） | 認証（Supabase Auth）・ファイル保管（Storage）・RLS もここ |
| API／画面 | Node.js（Express）を Vercel にデプロイ | サーバー側だけが `service_role` キーを持つ。ブラウザには `anon` キーのみ |
| 決済 | SBペイメントサービス（リダイレクト型またはトークン型） | カード情報は自社のサーバー・DBを一切通さない（第4.5節） |
| 署名画像・契約PDF | Supabase Storage（非公開バケット） | 署名付きURLで権限確認後に配信 |

### 1.2 命名と型の約束

- テーブル名・列名は **英語の snake_case**。日本語の画面名との対応は第13章の表で引く。
- 主キーは `bigint generated always as identity`。人が読む番号（`AP-202606-0012` など）は別列 `code` に持ち、**DB側の関数で採番**する（第1.4節）。
- **金額はすべて税込・整数（円）** → `integer`。小数は使わない。率は `numeric(6,4)`（例 0.0350）。
- 日付は `date`（日本の暦日）、日時は `timestamptz`（UTCで保存、表示時に JST）。
  「施工完了日」「締め月」など**業務の締めに使う日付は `date` 列を別に持ち、`timestamptz` から派生させない**（モックの `fmtDate()` と同じ考え方。UTC変換で1日ずれる事故を防ぐ）。
- **SQL の中で「今日」や「日時→日付」を取るときは、必ず次の関数を通す。** `current_date` や `timestamptz::date` は
  接続のタイムゾーン設定（Supabase の既定は UTC）に依存し、日本の朝9時までは前日になる。

```sql
create or replace function jst_today() returns date language sql stable as $$
  select (now() at time zone 'Asia/Tokyo')::date $$;
create or replace function jst_date(p timestamptz) returns date language sql immutable as $$
  select (p at time zone 'Asia/Tokyo')::date $$;
```
- 列挙値は PostgreSQL の `enum` 型ではなく **`text` + `check` 制約**にする（値の追加が `alter type` 不要で済み、Supabase のマイグレーションが簡単）。
- すべてのテーブルに `created_at timestamptz default now()`、更新があるものに `updated_at`（トリガーで更新）。
- 削除は原則しない。無効化は `status` や `disabled_at` で表す（過去の配分・請求を壊さないため）。

### 1.3 「確定値の書き込み」の原則（この設計で最も大事な考え方）

配分や手数料は **計算式を毎回走らせるのではなく、確定した時点の結果を行に書き込む**。

| いつ確定するか | 何を書き込むか | 書き込み先 |
|---|---|---|
| 申込の決済が成立した時（現金・請求書払いは申込受付時） | 適用した料率、決済手数料の額 | `applications.fee_rate_applied` / `fee_amount` |
| 同上 | 案件ごとの手数料按分、配分の基礎額、取次窓口 | `service_orders.fee_amount` / `base_amount` / `shop_id_snapshot` |
| **施工完了を報告した時** | 完了日（締め月の元）、**自社取次かどうか、本部／取次／施工代理店の配分額** | `service_orders.completed_on` / `self_served` / `*_share` |
| 月次の支払を確定した時 | 支払先ごとの合計、振込額、現金差引額 | `payout_statements` |

**配分額を確定させるのは施工完了時**（2026-09-23 利用者確定）。料率と手数料は決済時点で固定するが、
配分は「誰が施工したか」で決まるため、施工代理店が確定する完了時まで計算しない。
決済時に確定させると、差し戻して別の会社に割り当て直したときに古い配分が残り、支払先がずれる
（合計は売上と一致したままなので検算では気づけない）。支払対象はもともと施工完了の案件だけなので、
完了前に配分を持つ必要がない。**料率改定が過去に遡らないという目的は、料率を決済時点で固定することで満たされる。**

理由：料率の改定・取次機能の停止・配分ルールの見直しが起きても、**過去の確定済み月の金額が変わらない**ようにするため。
モックでは `splitOf()` を表示のたびに計算しているが、本番では「書き込み時に1回計算し、以後は読むだけ」にする。

### 1.4 採番（DB側で行う）

モックは「配列の件数＋1」で採番していたが、本番では同時アクセスで重複するため **PostgreSQL のカウンタ表を行ロックして**採番する。

| 対象 | 形式 | 例 | 仮／確定 |
|---|---|---|---|
| 申込 | `AP-YYYYMM-連番4桁` | AP-202606-0012 | 仮 |
| 施工案件 | 申込番号の枝番 `-N` | AP-202606-0012-1 | 仮（plan.md 第8節） |
| 消耗品注文 | `PO-YYYYMM-連番4桁` | PO-202606-0005 | 仮 |
| 請求書 | `INV-YYYYMM-連番3桁` | INV-202606-001 | **確定**（本部回答⑥） |
| 納品書 | `DN-YYYYMM-連番3桁` | DN-202606-001 | 仮 |
| 領収書 | `RC-YYYYMM-連番4桁` | RC-202606-0003 | 仮 |
| 取次窓口 | `SHOP-連番4桁` | SHOP-0007 | 仮（モック踏襲） |

```sql
create table code_counters (
  prefix  text not null,
  yyyymm  text not null,            -- 例 '202606'。年月で区切らない番号は '' を入れる
  last_no integer not null default 0,
  primary key (prefix, yyyymm)
);

create or replace function next_code(p_prefix text, p_date date, p_width int)
returns text language plpgsql as $$
declare v_ym text := coalesce(to_char(p_date, 'YYYYMM'), ''); v_no integer;
begin
  insert into code_counters(prefix, yyyymm, last_no) values (p_prefix, v_ym, 1)
    on conflict (prefix, yyyymm) do update set last_no = code_counters.last_no + 1
    returning last_no into v_no;
  return p_prefix || case when v_ym = '' then '' else '-' || v_ym end || '-' || lpad(v_no::text, p_width, '0');
end $$;
```

`insert … on conflict … returning` は同じ行に対して直列化されるため、同時に2件作っても同じ番号は出ない。

**請求書番号の「発行年月」は請求書の発行日（`issued_on`）の年月とする**（仮）。顧客請求は発行日＝締め月末なので、
7月に作成した6月分は `INV-202606-xxx` になる。請求書に印字される発行日と番号の年月が一致するのを優先した。
本部が「作成した月」を望む場合は `next_code` に渡す日付を `jst_today()` に変えるだけ（本部確認 第3回・3）。

### 1.5 権限の考え方（要約。詳細は第11章）

- ログインは Supabase Auth。`user_profiles` で「役割（hq／contractor／shop）」と「所属（どの施工代理店・どの取次窓口か）」を紐づける。
- **表示範囲の制御は RLS でDB側が強制**する。画面側の絞り込みは利便性のためで防御ではない。
- 金額を確定させる処理（決済成立、施工完了、月次支払確定、請求書の状態変更）は **サーバー側の関数（`security definer`）経由でのみ**行い、
  ブラウザから直接 `update` させない。確定値の列は RLS で更新不可にする。

## 2. 主体

登場人物は5種類。本部は1社しかないため専用テーブルは持たず、`settings` に会社情報（請求書の発行元）を置く。

```
本部（settings に会社情報）
 └ 施工代理店 contractors ── 担当者アカウント user_profiles(role=contractor)
      ├ 取次窓口 agency_shops（開拓した取次店）── 担当者アカウント user_profiles(role=shop)
      └ 取次窓口 agency_shops（self_of_contractor_id = 自社。取次機能をオンにすると自動作成）
法人顧客 corporate_customers（請求書払いの請求先。ログインしない）
```

### 2.1 施工代理店 `contractors`

```sql
create table contractors (
  id                 bigint generated always as identity primary key,
  name               text not null,
  contact_name       text,
  tel                text,
  email              text,                      -- 通知の送信先（第10章）
  region_label       text,                      -- 表示用「関東」など
  areas_label        text,                      -- 表示用「東京・埼玉・千葉」
  prefectures        text[] not null default '{}', -- 対応都道府県。割り当て候補の絞り込みに使う
  status             text not null default 'preparing'
                     check (status in ('preparing','active','dormant','terminated')),
  agency_enabled     boolean not null default false,  -- 取次機能（本部が付与）。メニュー出し分けはこの列で判定
  contract_date      date,
  renew_date         date,
  annual_target      integer,                   -- 年間目標件数（モックの target）
  demo_done          boolean not null default false,  -- 本部デモ実施済み
  available_weekdays smallint[] not null default '{1,2,3,4,5}', -- 0=日〜6=土
  ng_dates           date[] not null default '{}',
  -- 振込先は bank_accounts（第2.6節）に分ける。取次店がこの行を読むため、口座をここに置くと見えてしまう
  latitude           numeric(9,6), longitude numeric(9,6), geocoded_at timestamptz, -- 将来の距離判定用
  created_at         timestamptz not null default now(),
  updated_at         timestamptz not null default now()
);
```

- `agency_enabled` を true にするサーバー関数 `enable_agency(contractor_id)` が、自社取次窓口（`agency_shops.self_of_contractor_id = id`）が無ければ作る。
  false に戻すときは窓口の `status` を `suspended` にするだけで**削除しない**（過去案件の `shop_id` が指しているため）。
- 振込先は `bank_accounts` に持つ（第2.6節）。**自社取次窓口には振込先を持たせず、この会社の口座に振り込む**。

### 2.2 取次窓口 `agency_shops`

モックの `shops`。「取次店（他社）」と「施工代理店の自社取次窓口」を同じテーブルで持ち、`self_of_contractor_id` の有無で区別する。

```sql
create table agency_shops (
  id                     bigint generated always as identity primary key,
  code                   text not null unique,           -- SHOP-0007（トリガーで採番）
  name                   text not null,
  contractor_id          bigint not null references contractors(id), -- 開拓・管理する施工代理店
  self_of_contractor_id  bigint references contractors(id),          -- 自社取次窓口なら、その施工代理店。通常の取次店は null
  shop_type              text,                          -- 中古車販売／パーツ販売／施工代理店の自社取次 など
  contact_name           text, tel text, email text,
  prefecture             text,
  status                 text not null default 'preparing'
                         check (status in ('preparing','active','suspended','terminated')),
  qr_token               text not null unique default encode(gen_random_bytes(16),'hex'), -- 申込フォームURLの識別子（第3.7節）
  joined_on              date,
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
  constraint self_shop_belongs_to_owner check (self_of_contractor_id is null or self_of_contractor_id = contractor_id)
);
create unique index agency_shops_one_self_per_contractor
  on agency_shops(self_of_contractor_id) where self_of_contractor_id is not null;
```

- 判定関数（モックの `isSelfServed`）：**案件の `shop_id` の窓口の `self_of_contractor_id` が、案件の `contractor_id` と一致するか**。率の定数で判定しない。
- 申込フォームのURLは `https://…/apply/{qr_token}`。窓口の `status` が `active` でなければフォームを受け付けない。

### 2.3 法人顧客 `corporate_customers`

請求書払いの請求先。モックは `billing.corp`（法人名）で束ねていたが、本番は **このテーブルのIDで束ねる**（同名の別法人・表記ゆれ対策）。

```sql
create table corporate_customers (
  id            bigint generated always as identity primary key,
  name          text not null,                 -- 株式会社船橋オートサービス
  department    text, contact_name text, tel text, email text,
  postal_code   text, address text,
  created_by_shop_id bigint references agency_shops(id),  -- 最初に登録した取次窓口（RLSの参照範囲に使う）
  approval_status text not null default 'not_required'
                check (approval_status in ('not_required','pending','approved','rejected')), -- ①' 用の余白
  merged_into_id bigint references corporate_customers(id), -- 本部が重複を統合したとき、残す側の行を指す
  created_at timestamptz not null default now(), updated_at timestamptz not null default now()
);
```

- **同じ法人を別々の取次店が登録すると2行になる**（取次店は自店が登録した法人しか見えないため防げない）。
  そのまま月末を迎えると顧客請求が2枚に割れる。本部が顧客請求の画面で重複に気づいたら `merge_corporate_customers(from, to)` で統合する。
  統合は行を消さず `merged_into_id` を埋め、以後の申込・請求は統合先のIDで束ねる（過去の請求書の参照は壊さない）。

- 取次窓口が申込フォームで法人請求先を入力すると、同じ窓口の既存法人から選ぶか新規作成する。**申込には法人IDと、入力時点の名称・住所のスナップショット**の両方を持つ（第3.1節）。請求書の宛先はスナップショットを使う（後から法人マスタを直しても送付済み請求書が変わらない）。

### 2.4 担当者アカウント `user_profiles`（Supabase Auth との紐づけ）

```sql
create table user_profiles (
  user_id        uuid primary key references auth.users(id) on delete cascade,
  role           text not null check (role in ('hq','contractor','shop')),
  contractor_id  bigint references contractors(id),   -- role=contractor のとき必須
  shop_id        bigint references agency_shops(id),  -- role=shop のとき必須
  display_name   text not null,
  is_active      boolean not null default true,       -- 退職・契約終了時に false（Auth 側も無効化）
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
  constraint role_scope check (
    (role = 'hq'         and contractor_id is null and shop_id is null) or
    (role = 'contractor' and contractor_id is not null and shop_id is null) or
    (role = 'shop'       and shop_id is not null and contractor_id is null))
);
```

- **同じ施工代理店・取次窓口に複数の担当者を作れる**（1社1アカウントに固定しない）。
- 自社取次窓口には `shop` 役割のアカウントを作らない。兼業の会社は `contractor` としてログインし、`agency_enabled` で注文フォームが出る。
- アカウント発行は本部が行う。サーバー側で `auth.admin.createUser` → `user_profiles` 挿入 → 初期パスワード設定メール送付、を1つの関数にまとめる。
- 本部アカウントは二要素認証を必須にする（Supabase Auth の MFA）。
- RLS では `auth.uid()` からこの表を引く。頻繁に使うため、次のヘルパー関数を用意する（`security definer` で RLS を回避し、無限再帰を避ける）。

```sql
create or replace function current_role_info()
returns table(role text, contractor_id bigint, shop_id bigint)
language sql stable security definer set search_path = public as $$
  select role, contractor_id, shop_id from user_profiles where user_id = auth.uid() and is_active
$$;
create or replace function is_hq() returns boolean language sql stable as $$
  select exists (select 1 from current_role_info() where role = 'hq') $$;
create or replace function my_contractor_id() returns bigint language sql stable as $$
  select contractor_id from current_role_info() $$;
create or replace function my_shop_id() returns bigint language sql stable as $$
  select shop_id from current_role_info() $$;
```

### 2.5 本部の設定 `settings`

1行だけのテーブル。請求書の発行元情報と、本部回答で切り替わるスイッチをここに置く。

```sql
create table settings (
  id                        boolean primary key default true check (id), -- 常に1行
  issuer_name               text not null,   -- 株式会社ワイズ
  issuer_address            text not null,
  issuer_tel                text not null,
  issuer_bank_text          text not null,   -- 関西みらい銀行 東大阪中央支店 普通 XXXXXXX カブシキガイシャワイズ（本番で実値）
  issuer_invoice_reg_no     text not null,   -- T6122001039578
  hq_rate                   numeric(6,4) not null default 0.10,
  shop_rate                 numeric(6,4) not null default 0.10,
  contractor_rate           numeric(6,4) not null default 0.80,
  offset_cash_remit         boolean not null default false,  -- ③'' 相殺するか（仮：しない）
  customer_invoice_due_rule text not null default 'end_of_next_month', -- ②'
  customer_invoice_fee_note text not null default '振込手数料はお客さまのご負担にてお願いいたします', -- ③'
  receipt_issuer            text not null default 'hq' check (receipt_issuer in ('hq','contractor')), -- ⑤'
  supply_free_shipping_threshold integer not null default 15000,
  supply_shipping_fee       integer not null default 1000,
  invoice_due_days          integer not null default 30,  -- 消耗品・加盟金・現金回収の支払期限
  min_lead_business_days    integer not null default 3,   -- 通常の取次店の最短希望日（自社取次は0）
  payment_timeout_hours     integer not null default 24,  -- カード／PayPay で決済が完了しない申込を無効にするまでの時間（第4.7節）
  updated_at timestamptz not null default now()
);
```

配分率（10/10/80）は `settings` に置くが、**確定値は案件に書き込む**ので、ここを変えても過去の案件は変わらない（第1.3節）。
この表に伏せるべき情報はない（発行元の口座は請求書に印字される。配分率はモックでも施工代理店の画面に出している）ので、
ログイン済みの全員に読み取りを許す。専用のビューは作らない。

### 2.6 振込先 `bank_accounts`

口座情報は主体のテーブルから切り離す。取次店は担当施工代理店の名前・連絡先を見る必要があり、その行を読ませると
同じ行にある口座番号まで見えてしまうため（ビューで列を隠しても、元テーブルを直接読めば出る）。

```sql
create table bank_accounts (
  id             bigint generated always as identity primary key,
  owner_type     text not null check (owner_type in ('contractor','shop')),
  contractor_id  bigint references contractors(id),

  bank_name      text not null, branch_name text not null,
  account_type   text not null check (account_type in ('ordinary','current')),  -- 普通／当座
  account_no     text not null,
  account_holder text not null,                  -- カナ名義（振込CSV用）

create unique index bank_accounts_active_contractor on bank_accounts(contractor_id) where owner_type='contractor' and is_active;
create unique index bank_accounts_active_shop       on bank_accounts(shop_id)       where owner_type='shop' and is_active;
-- 自社取次窓口は口座を持たない（施工代理店の口座に振り込む）
create or replace function bank_accounts_no_self_shop() returns trigger language plpgsql as $$
```

- 読める人：本部、口座の持ち主（施工代理店は自社の口座と、自社が開拓した取次店の口座）。取次店は自店の口座のみ。
- 月次支払を確定するとき、そのときの有効な口座を `payout_statements.bank_snapshot` に写す（後から口座を変えても明細は変わらない）。

## 3. 申込と施工案件（申込1:案件N）

モックの `serviceOrders` は「1申込＝1台」だったが、本番では **申込（`applications`）1件に施工案件（`service_orders`）N件**をぶら下げる（plan.md 第8節）。

```
applications（申込）                     service_orders（施工案件＝車両1台）
  取次窓口・お客さま情報・区分・支払方法      車種・区分・やにとり・金額・車両番号
  請求先（法人）・希望日・希望時間            施工代理店（申込単位で決めた値を写す）
  決済1回・手数料・現金の回収記録            施工日・施工前確認の署名・完了報告・完了日
  承認ステータス（①'の余白）                手数料の按分・配分の確定値
```

**どちらに持つか**の判断基準：「決済・請求・訪問」に関わるものは申込、「車1台の作業・証跡・配分」は案件。
モックの1画面（施工注文管理）は本番では案件の一覧で、申込番号でグループ表示する。

### 3.1 申込 `applications`


- **申込の状態は持たない。** 配下の案件から導出する（全案件が完了なら完了、1件でも新規受付なら受付中…）。表示用のビュー `application_summary` で計算する（第3.4節）。
- `payment_status`：カード／PayPay は決済代行会社の結果通知（Webhook）で `paid` になる。現金・請求書払いは `not_applicable`（決済代行を通らない）。

- 最短希望日のチェック（通常の窓口は3営業日後以降、自社取次は当日可）は**サーバー側の受付関数**で行う。DBの制約にはしない（祝日表を参照するため）。

### 3.2 施工案件 `service_orders`

```sql
create table service_orders (
  id                 bigint generated always as identity primary key,
  code               text not null unique,              -- AP-202606-0012-1（申込番号の枝番）
  application_id     bigint not null references applications(id),
  seq_no             smallint not null,                 -- 枝番 1,2,…
  -- 車両
  car_name           text not null,                     -- 入力された車種名
  car_class          text not null check (car_class in ('kei','standard','onebox')),
  car_class_source   text not null default 'dictionary' check (car_class_source in ('dictionary','manual')), -- 辞書判定か手動か
  yani_option        boolean not null default false,
  vehicle_no         text,                              -- 車両番号（ナンバー下4桁など。任意）
  amount             integer not null check (amount > 0),   -- この1台の施工料金（税込。基本料金＋やにとり）
  -- 施工（案件単位）
  status             text not null default 'pending_payment'
                     check (status in ('pending_payment','new','pending_contractor','scheduled','pre_checked','completed','cancelled')),
                     -- pending_payment＝カード／PayPay の決済待ち。本部の一覧には出さない（第4.7節）
  contractor_id      bigint references contractors(id), -- 申込の contractor_id を写す（将来、車両ごとに分けられる余地）
  scheduled_on       date,
  completed_at       timestamptz,
  completed_on       date,                              -- 締め月の元。completed_at を JST で切った日付（関数で書き込む）
  completed_by       uuid references auth.users(id),
  -- 確定値（第4・5章。以後は更新不可）
  -- fee_amount / base_amount / shop_id_snapshot は決済成立時（fix_fees）、
  -- self_served と各配分額は施工完了時（fix_shares）に書き込む
  fee_amount         integer,                           -- 申込の手数料をこの案件に按分した額
  base_amount        integer,                           -- amount − fee_amount
  self_served        boolean,                           -- 取次窓口の self_of_contractor_id = contractor_id だったか
  hq_rate_applied numeric(6,4), shop_rate_applied numeric(6,4), contractor_rate_applied numeric(6,4),
  hq_share           integer,
  shop_share         integer,                           -- 自社取次なら 0
  contractor_share   integer,                           -- 自社取次なら base×90%
  shares_fixed_at    timestamptz,                       -- 配分を確定した時刻。null なら未完了（＝支払対象外）
  shop_id_snapshot   bigint references agency_shops(id), -- 配分計算時の取次窓口（申込の shop_id の写し）
  -- 請求との紐づけ（第6章）
  cash_collection_invoice_id bigint,                    -- 現金回収請求書（施工代理店宛て）
  customer_invoice_id        bigint,                    -- 顧客請求書（法人宛て）
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
  unique (application_id, seq_no),
  -- 1円一致。確定済みなのに列が空、という状態も拒否する（空値が混ざると式全体が空になり check を素通りするため）
  constraint shares_sum check (
    shares_fixed_at is null
    or (fee_amount is not null and hq_share is not null and shop_share is not null and contractor_share is not null
        and fee_amount + hq_share + shop_share + contractor_share = amount))

create index service_orders_app_idx on service_orders(application_id);
create index service_orders_contractor_status_idx on service_orders(contractor_id, status);
create index service_orders_completed_on_idx on service_orders(completed_on);
```

`shares_sum` 制約が「決済手数料＋本部＋取次＋施工代理店＝売上」の1円一致をDBで保証する。

### 3.3 状態遷移（案件）

| 状態 | 日本語（モック） | 誰が進めるか | 条件 |
|---|---|---|---|
| `pending_payment` | （モックにない）決済待ち | 受付関数 | カード／PayPay の申込は必ずここから。決済代行会社の通知で `new` へ。**本部の一覧には出さない** |
| `new` | 新規受付 | 決済通知 ／ 現金・請求書払いは受付時に直接ここ | 通常の取次窓口からの申込 |
| `pending_contractor` | 施工店確認中 | 本部が割り当て | `contractor_id` を設定し通知（第10章） |
| `scheduled` | 施工日確定 | 施工代理店が受諾 ／ 自社取次は受付（決済完了）時に直接ここ | `scheduled_on` を設定 |
| `pre_checked` | 施工前確認済み | 署名の送信（第3.5節） | `pre_check_signatures` に行がある |
| `completed` | 施工完了 | 施工代理店の完了報告 | **現金の申込は `cash_collected_at` が必須**（ゲート） |
| `cancelled` | （モックにない） | 本部 ／ 決済期限切れの自動処理 | 決済済みなら返金の記録を残す |

**許可する遷移**（これ以外はトリガーで拒否する）：

| から ＼ へ | new | pending_contractor | scheduled | pre_checked | completed | cancelled |
|---|---|---|---|---|---|---|
| `pending_payment` | 決済完了（通常窓口） | | 決済完了（自社取次） | | | 決済期限切れ・決済失敗 |
| `new` | | 本部が割り当て | | | | 本部 |
| `pending_contractor` | 施工代理店が対応不可 | | 施工代理店が受諾 | | | 本部 |
| `scheduled` | 施工代理店が対応不可（施工前のみ） | | | 署名送信 | | 本部 |
| `pre_checked` | | | | | 完了報告 | 本部（署名は残す） |
| `completed` | | | | | | **不可**（訂正は返金＋新規申込） |
| `cancelled` | | | | | | |

- 「対応不可」は**申込単位**（割り当てが申込単位で1社のため）。申込配下の案件に1件でも `pre_checked` 以降があれば差し戻せない。
  差し戻すと配下の案件を `new` に戻し、案件と申込の `contractor_id`・`scheduled_on` を空にする。
- **`completed` からは動かさない**（配分と締めが確定するため）。誤って完了にした場合は本部が返金処理と新しい申込で対応する。
- 遷移はすべて関数（`confirm_payment`, `assign_contractor`, `accept_job`, `decline_application`, `submit_pre_check`, `complete_job`, `cancel_application`）経由。

```sql
create or replace function complete_job(p_order_id bigint) returns void
language plpgsql security definer set search_path = public as $$
declare v record;
begin
  select so.status, so.contractor_id, a.payment_method, a.cash_collected_at into v
    from service_orders so join applications a on a.id = so.application_id
   where so.id = p_order_id for update of so;
  if v.contractor_id is distinct from my_contractor_id() and not is_hq() then raise exception 'not your job'; end if;
  if v.status <> 'pre_checked' then raise exception 'pre-check signature required'; end if;
  if v.payment_method = 'cash' and v.cash_collected_at is null then raise exception 'cash not collected'; end if;
  update service_orders set status = 'completed', completed_at = now(),
         completed_on = jst_today(), completed_by = auth.uid()
   where id = p_order_id;
  perform fix_shares(p_order_id);   -- 配分はここで確定する（第5.1節）
end $$;
```

この関数は**ブラウザから、ログイン中の利用者の認証情報で**呼ぶ（第11.1節）。管理者キーで呼ぶと利用者が空になり、本部でも弾かれる。

### 3.4 申込の導出状態（ビュー）

```sql
create view application_summary with (security_invoker = on) as
select a.id, a.code, a.shop_id, a.contractor_id, a.payment_method, a.payment_status, a.total_amount,
       count(so.id)                                            as order_count,
       count(*) filter (where so.status = 'completed')         as completed_count,
       count(*) filter (where so.status = 'cancelled')         as cancelled_count,
       case
         when bool_and(so.status = 'cancelled')                          then 'cancelled'
         -- 以下はキャンセル分を除いて判定する（1台キャンセル＋残り完了 を「完了」と出すため）
         when bool_and(so.status in ('completed','cancelled'))           then 'completed'
         when bool_or(so.status = 'pending_payment')                     then 'pending_payment'
         when bool_or(so.status = 'new')                                 then 'new'
         when bool_or(so.status = 'pending_contractor')                  then 'pending_contractor'
         when bool_or(so.status = 'scheduled')                           then 'scheduled'
         else 'pre_checked' end                                          as derived_status
from applications a join service_orders so on so.application_id = a.id
group by a.id;
```

- `security_invoker = on` で元テーブルの RLS を通す（第11章）。
- 自社取次かどうかは案件の `self_served`（完了時の確定値）を見る。ビューで計算し直さない（二重の真実を作らない）。

### 3.5 施工前確認の署名 `pre_check_signatures`

技術仕様書 5.5節（`valuables_confirmations`）を案件単位に置き直したもの。**車両ごとに署名**する。

```sql
create table pre_check_signatures (
  id                 bigint generated always as identity primary key,
  service_order_id   bigint not null references service_orders(id),
  contractor_id      bigint not null references contractors(id),  -- 送信者の所属（サーバーがセッションから入れる）
  submitted_by       uuid not null references auth.users(id),
  storage_path       text not null,          -- Storage の非公開バケット内パス（signatures/{order_id}/{uuid}.png）

  checklist          jsonb not null,         -- {valuables_confirmed: true, ...} 確認項目の内容
  signed_at          timestamptz not null default now(),  -- サーバー時刻。クライアントの時刻は使わない
```

- **更新・削除を許さない**（RLS で `update`/`delete` のポリシーを作らない＝誰もできない）。訂正は新しい行を追加し、古い行の `superseded_by` だけをサーバー関数で埋める。

### 3.7 申込の受付（お客さまがQRから直接申し込む）

モックの注文フォームは「お客さまがQRコードを読み取ると、この画面がスマホで開きます」と明記されている。
つまり**申込フォームはログインなしでお客さま自身が使う**。取次店の担当者が代理入力する場合と、施工代理店が
自社窓口で受け付ける場合（ログイン済み）も同じ関数を通す。

| 入口 | 誰が | ログイン | `submitted_via` | 識別 |
|---|---|---|---|---|
| QRのURL `/apply/{qr_token}` | お客さま | なし | `customer_qr` | `qr_token` → 取次窓口 |
| 取次店の画面 | 取次店の担当者 | あり | `shop_staff` | セッションの `shop_id` |
| 施工代理店の画面「注文フォーム（自社取次）」 | 施工代理店の担当者 | あり | `contractor_self` | セッションの `contractor_id` → 自社窓口 |

**未認証の書き込み経路**なので、テーブルへの直接 `insert` は誰にも許さず、`submit_application` 関数だけを `anon` ロールに実行許可する。
関数の中で次を検証する。

1. `qr_token` が存在し、その窓口の `status = 'active'`（停止中・準備中の窓口では受け付けない）。
2. 明細行が1件以上、各行の車種区分と価格が `service_prices` の有効な値と一致する（金額はクライアントから受け取らず、サーバーで引き直す）。
3. 希望日が最短日以降（通常窓口＝`settings.min_lead_business_days` 営業日後、自社取次＝当日可。`holidays` 表で営業日を数える）。
4. 請求書払いは法人のみ・請求先が揃っている。
5. 同じ `qr_token` からの受付数が短時間に多すぎない（**Express 側でIPと窓口ごとのレート制限**。DB側は件数の上限だけ持つ）。

- お客さまの申込は `created_by = null`。取次窓口は `shop_id` で分かる。
- カード／PayPay は申込と案件を `pending_payment` で作り、決済代行会社の画面へ渡す。現金・請求書払いは `new`（自社取次は `scheduled`）で作る。
- ボット対策：フォームに見えない入力欄（ハニーポット）を置き、値が入っていれば黙って捨てる。CAPTCHA は施工現場での入力を妨げるため第一段階では入れない。
- 未決済のまま放置された申込の扱いは第4.7節。

## 4. 決済

### 4.1 決済手段

| 手段 | 個人 | 法人 | 決済代行 | 手数料 | 回収する人 |
|---|---|---|---|---|---|
| `card` | ○ | ○ | SBペイメントサービス | あり（ブランド別） | 決済代行会社 |
| `paypay` | ○ | ○ | SBペイメントサービス（1社でまとめられる前提。未回答） | あり | 決済代行会社 |
| `cash` | ○ | ○ | 通さない | 0% | **施工代理店（施工時）** |
| `invoice` | × | ○ | 通さない | 0% | 本部（月末締め請求書） |

### 4.2 料率テーブル `payment_fee_rates`（手段×ブランド×有効期間）

```sql
create table payment_fee_rates (
  id             bigint generated always as identity primary key,
  payment_method text not null check (payment_method in ('card','paypay','cash','invoice')),
  card_brand     text,                        -- card のとき VISA/MASTER/JCB/AMEX/DINERS。ブランドを問わない行は null
  rate           numeric(6,4) not null check (rate >= 0 and rate < 1),
  valid_from     date not null,
  valid_to       date,                        -- null = 現在有効。改定時に前の行の valid_to を埋めて新しい行を追加
  note           text,
  created_at timestamptz not null default now(),
  constraint valid_range check (valid_to is null or valid_to >= valid_from)
);
-- 同じ手段・ブランドで有効期間が重ならないこと
alter table payment_fee_rates add constraint fee_rates_no_overlap
  exclude using gist (payment_method with =, coalesce(card_brand,'') with =,
                      daterange(valid_from, coalesce(valid_to, 'infinity'::date), '[]') with &&);
```

初期データ（仮。②の回答で差し替え）：

| payment_method | card_brand | rate | valid_from |
|---|---|---|---|
| card | null | 0.0350 | 2026-04-01 |
| paypay | null | 0.0350 | 2026-04-01 |
| cash | null | 0.0000 | 2026-04-01 |
| invoice | null | 0.0000 | 2026-04-01 |

料率の選択関数：ブランド一致の行を優先し、無ければブランド null の行。**基準日は決済成立日（現金・請求書払いは受付日）**。

```sql
create or replace function pick_fee_rate(p_method text, p_brand text, p_on date)
returns payment_fee_rates language sql stable as $$
  select * from payment_fee_rates
   where payment_method = p_method and p_on >= valid_from and (valid_to is null or p_on <= valid_to)
     and (card_brand = p_brand or card_brand is null)
   order by card_brand nulls last limit 1
$$;
```

`gist` の排他制約には `btree_gist` 拡張が要る（Supabase で有効化可能）。

### 4.3 手数料の計算と案件への按分（決済1回＝申込1件）

plan.md 第8節のとおり、**手数料は申込の合計に料率をかけて1回だけ算出し、案件に金額比で按分**する。端数は最後の案件に寄せる。

```
fee_total = round(total_amount × rate)
案件 i（最後以外）: fee_i = floor(fee_total × amount_i / total_amount)
最後の案件:          fee_n = fee_total − Σ fee_i
```

按分は施工代理店が誰かに関係なく決まるので、**決済成立（Webhook）または現金・請求書払いの受付時**に関数 `fix_fees(application_id)` で
1回だけ書き込む。`applications.fee_amount` が入っていたら二度目は拒否する。書き込むのは次の4つ。

| 書き込む先 | 内容 |
|---|---|
| `applications.fee_rate_id` / `fee_rate_applied` / `fee_amount` | 適用した料率行・率・手数料合計 |
| `service_orders.fee_amount` | 上の式で按分した額 |
| `service_orders.base_amount` | `amount − fee_amount`（配分の基礎） |
| `service_orders.shop_id_snapshot` | 決済時点の取次窓口 |

**配分額（本部／取次／施工代理店）はここでは計算しない。** 施工完了時に `fix_shares(service_order_id)` で確定する（第5.1節）。

> 申込の一部の案件を後からキャンセルした場合、その案件が持つ手数料は誰にも配られないまま残る。
> 1円一致は案件ごとに保たれるので破綻しないが、返金処理の中で按分をやり直すかは運用を決めてから実装する。

### 4.4 決済代行会社との連携 `payment_transactions`

申込には最終結果だけを持ち、代行会社とのやり取りの生ログは別テーブルに残す（返金・二重通知・照合のため）。

```sql
create table payment_transactions (
  id                 bigint generated always as identity primary key,
  application_id     bigint not null references applications(id),
  provider           text not null default 'sbps',
  provider_txn_id    text not null,
  kind               text not null check (kind in ('authorize','capture','refund','cancel','notify')),
  status             text not null,            -- 代行会社の状態文字列をそのまま
  amount             integer not null,
  payload            jsonb,                    -- 通知本文（カード情報は含まれない前提。含まれる項目は保存前に落とす）
  received_at        timestamptz not null default now(),
  unique (provider, provider_txn_id, kind)     -- 同じ通知を二重に処理しない
);
```

### 4.5 カード情報を持たない構成（再確認）

- 決済画面は代行会社が提供するもの（リダイレクト型／トークン型）。自社の画面・サーバー・DBにカード番号・有効期限・セキュリティコードは**一切通らない**。
- DBに置くのは `psp_transaction_id`、ブランド名、下4桁（代行会社が返す場合のみ・任意）、金額、結果。
- モックの `openPaymentModal` は本番に持ち込まない。
- 決済画面のページには解析タグ・広告タグを入れない（PCI DSS の簡易区分を保つため）。

### 4.6 返金・キャンセル

- `cancelled` にする前に決済済みなら、代行会社で返金 → `payment_transactions(kind='refund')` → `applications.payment_status='refunded'`。
- 配分の確定値は**消さない**。締め月に含めないよう、`service_orders.status='cancelled'` の案件は月次支払の対象外にする（第5.3節）。

### 4.7 決済待ちの申込と、決済されないまま放置された申込

リダイレクト型の決済では、**申込の行を作ってから**決済代行会社の画面へ渡す（案件番号を渡す必要があるため）。
お客さまがその画面で離脱すると、申込は `payment_status='unpaid'` のまま残る。これを本部の一覧に出すと、
未払いの案件に施工代理店を割り当ててしまう。

- カード／PayPay の申込は案件を **`pending_payment`** で作る。本部の施工注文管理・ダッシュボード・割り当て候補は
  `pending_payment` を**含めない**（RLS ではなく画面の絞り込み。データとしては本部が見られる）。
- 決済代行会社の成功通知（Webhook）を受けた `confirm_payment(application_id, txn)` が、`payment_status='paid'`・`paid_at`・`card_brand` を書き、
  `fix_fees` を呼び、案件を `new`（自社取次は `scheduled`）へ進める。**この関数だけが `pending_payment` から先へ進める。**
- 失敗通知は `payment_status='failed'` にし案件を `cancelled`。
- **期限切れ**：`applied_on` の受付から `settings.payment_timeout_hours`（仮 24時間）を過ぎても `unpaid` の申込は、
  定期処理（Vercel Cron → `expire_unpaid_applications()`）で `payment_status='failed'`・案件 `cancelled`・
  `service_order_events` に `payment_expired` を残す。決済代行会社側のセッション有効期限より長くとる。
- 期限切れ後に成功通知が届いた場合（稀）：`confirm_payment` は `cancelled` の案件を進めず、`payment_transactions` に記録して
  本部へ通知する（本部が返金するか、案件を作り直すかを判断）。

## 5. 配分と精算

### 5.1 案件ごとの配分（モックの `splitOf` をDB関数に）

```
base       = amount − fee              （fee は第4.3節で按分した額）
self_served = 取次窓口.self_of_contractor_id = 案件.contractor_id
shop       = self_served ? 0 : round(base × shop_rate)
contractor = round(base × (self_served ? contractor_rate + shop_rate : contractor_rate))
hq         = base − shop − contractor   （残り全額。合計を売上に一致させる）
```

- 四捨五入は「振込額になる取次店・施工代理店を先に確定し、残りを本部」。モックと同じ。
- **案件ごとに計算してから合算**する。申込単位で計算してから割らない。
- 率は `settings` の現在値を読み、`*_rate_applied` に写す。以後 `settings` を変えても案件は変わらない。

確定は2段階に分ける。**手数料は決済時、配分は施工完了時。**

```sql
-- ① 決済成立時（現金・請求書払いは受付時）。誰が施工するかに関係なく決まる部分だけを確定する。
create or replace function fix_fees(p_application_id bigint) returns void
language plpgsql security definer set search_path = public as $$
declare a applications%rowtype; r payment_fee_rates; o record;
        v_fee_total int; v_fee_acc int := 0; v_n int; v_i int := 0; v_fee int;
begin
  select * into a from applications where id = p_application_id for update;
  if a.fee_amount is not null then return; end if;   -- 冪等：決済代行会社は通知を再送するので、二度目は黙って成功させる
  r := pick_fee_rate(a.payment_method, a.card_brand, coalesce(jst_date(a.paid_at), a.applied_on));
  if r.id is null then raise exception 'no fee rate for % on %', a.payment_method, a.applied_on; end if;
  v_fee_total := round(a.total_amount * r.rate);
  update applications set fee_rate_id = r.id, fee_rate_applied = r.rate, fee_amount = v_fee_total where id = a.id;
  select count(*) into v_n from service_orders where application_id = a.id;
  for o in select * from service_orders where application_id = a.id order by seq_no loop
    v_i := v_i + 1;
    v_fee := case when v_i = v_n then v_fee_total - v_fee_acc
                  else floor(v_fee_total::numeric * o.amount / a.total_amount) end;
    v_fee_acc := v_fee_acc + v_fee;
    update service_orders set fee_amount = v_fee, base_amount = o.amount - v_fee, shop_id_snapshot = a.shop_id
     where id = o.id;
  end loop;
end $$;

-- ② 施工完了時。complete_job の中から呼ぶ。ここではじめて「誰が施工したか」が決まる。
create or replace function fix_shares(p_service_order_id bigint) returns void
language plpgsql security definer set search_path = public as $$
declare o service_orders%rowtype; s settings%rowtype;
        v_self boolean; v_shop int; v_ctr int; v_shop_self bigint;
begin
  select * into o from service_orders where id = p_service_order_id for update;
  if o.shares_fixed_at is not null then raise exception 'shares already fixed'; end if;
  if o.base_amount is null then raise exception 'fees not fixed yet'; end if;
  if o.contractor_id is null then raise exception 'contractor not assigned'; end if;
  select * into s from settings;
  select self_of_contractor_id into v_shop_self from agency_shops where id = o.shop_id_snapshot;
  v_self  := (v_shop_self is not null and v_shop_self = o.contractor_id);
  v_shop  := case when v_self then 0 else round(o.base_amount * s.shop_rate) end;
  v_ctr   := round(o.base_amount * (s.contractor_rate + case when v_self then s.shop_rate else 0 end));
  update service_orders set self_served = v_self,
    hq_rate_applied = s.hq_rate, shop_rate_applied = s.shop_rate, contractor_rate_applied = s.contractor_rate,
    shop_share = v_shop, contractor_share = v_ctr, hq_share = o.base_amount - v_shop - v_ctr,
    shares_fixed_at = now()
   where id = p_service_order_id;
end $$;
```

> **④'（取次店自身が顧客）の扱い**：仮の設定は「特別扱いなし・取次分10%を付ける」なので、`fix_shares` は
> `applications.shop_is_customer` を参照しない。本部が「付けない」と回答した場合にだけ、この関数に
> 「`shop_is_customer` なら `v_shop = 0`、施工代理店の率も上げない（本部が10%を取る）」という分岐を足す。
> 列は第3.1節に用意済みなのでテーブルの変更は要らない。

> **差し戻して別の会社に割り当て直しても配分は狂わない**。配分を書き込むのは完了時の1回だけで、
> そのときの `contractor_id` で自社取次かどうかを判定するため。完了後は状態を巻き戻せず、
> `contractor_id` の変更もトリガーで拒否する（第11.4節）。

### 5.2 支払対象と締め月

- **支払対象は `status='completed'` の案件のみ。** 締め月は `completed_on` の年月（受付日・施工日ではない）。
- 未完了の案件は「受取見込み」として参考表示するだけで、支払データには入れない。
- 月次の集計は次のビューで見る（確定前の下書きにあたる）。

```sql
create view payout_preview as
select to_char(so.completed_on, 'YYYY-MM') as settlement_month,
       so.id as service_order_id, so.code, so.application_id, a.shop_id, so.contractor_id,
       a.payment_method, so.amount, so.fee_amount, so.base_amount, so.self_served,
       so.hq_share, so.shop_share, so.contractor_share,
       sh.self_of_contractor_id as shop_self_of         -- 自社窓口が取り次いで他社が施工した案件の判定に使う
from service_orders so
join applications a on a.id = so.application_id
join agency_shops sh on sh.id = so.shop_id_snapshot
where so.status = 'completed' and so.shares_fixed_at is not null;
```

### 5.3 月次の支払明細 `payout_statements`（支払先×締め月で1行）

モックの `payoutRows(month)` の1行に相当。**本部が「この月の支払を確定」した時点で作成**し、以後は案件を動かしても変わらない。

```sql
create table payout_statements (
  id                 bigint generated always as identity primary key,
  settlement_month   text not null,                -- '2026-06'
  payee_type         text not null check (payee_type in ('contractor','shop')),
  contractor_id      bigint references contractors(id),
  shop_id            bigint references agency_shops(id),     -- payee_type=shop（自社取次窓口は支払先にしない）
  job_count          integer not null,             -- 施工した案件数（施工代理店）／取り次いだ案件数（取次店）
  referred_count     integer not null default 0,   -- 自社窓口で取り次ぎ他社が施工した案件数（施工代理店のみ）
  sales_amount       integer not null,             -- 対象案件の売上合計
  share_amount       integer not null,             -- 取り分（施工代理店：contractor_share＋自社窓口の shop_share／取次店：shop_share）
  cash_job_count     integer not null default 0,   -- 現金案件数（施工代理店のみ）
  cash_sales_amount  integer not null default 0,
  cash_kept_amount   integer not null default 0,   -- 現金案件の contractor_share（手元に残す分）
  cash_remit_amount  integer not null default 0,   -- 現金案件の amount − contractor_share（本部へ振込む20%）
  transfer_amount    integer not null,             -- 振込額（第5.5節の相殺の有無で決まる）
  offset_applied     boolean not null default false, -- 相殺して transfer_amount を出したか
  bank_snapshot      jsonb,                        -- 確定時点の振込先（bank_accounts の有効な行の写し。後から口座を変えても明細は変えない）
  status             text not null default 'fixed' check (status in ('fixed','transferred','cancelled')),
  transferred_on     date,
  fixed_by           uuid references auth.users(id),
  created_at timestamptz not null default now(),
  constraint payee_ref check ((payee_type='contractor' and contractor_id is not null and shop_id is null)
                           or (payee_type='shop' and shop_id is not null and contractor_id is null))
);

-- 支払先×締め月で1行。4列まとめた unique は使えない（下の注意を参照）ので、種別ごとの部分一意索引にする。
create unique index payout_statements_contractor_uq on payout_statements(settlement_month, contractor_id)
  where payee_type = 'contractor' and status <> 'cancelled';
create unique index payout_statements_shop_uq on payout_statements(settlement_month, shop_id)
  where payee_type = 'shop' and status <> 'cancelled';

create table payout_statement_lines (       -- 明細：どの案件が含まれたか（監査・再計算防止）
  statement_id       bigint not null references payout_statements(id),
  service_order_id   bigint not null references service_orders(id),
  line_kind          text not null check (line_kind in ('performed','referred')), -- 施工分／自社窓口取次分
  amount             integer not null,     -- この行で支払う額
  description        text not null,        -- 案件の説明の写し（完了日・車種・区分・金額）。案件を読めない相手でも根拠が分かるようにする
  voided_at          timestamptz,          -- 明細を取り消した時刻。取消は行を消さずここを埋める（監査のため）
  primary key (statement_id, service_order_id, line_kind)
);

-- **二重払いを最終的に止めるのはこの索引**：1つの案件は、同じ区分では一度しか支払われない。
create unique index payout_statement_lines_once on payout_statement_lines(service_order_id, line_kind)
  where voided_at is null;
```

> **なぜ4列の `unique` では防げないか**：PostgreSQL の一意制約は既定で空値どうしを別の値として扱う。
> 施工代理店の行は `shop_id` が空、取次店の行は `contractor_id` が空なので、**どの行も必ず空値を1つ含み**、
> 制約が一度も働かない。同じ月・同じ支払先の明細を何行でも作れてしまう。種別で絞った部分一意索引ならこの問題がない。

> **案件番号で押さえるほうが確実**（2026-09-23 利用者指摘）：上の見出し側の索引は「同じ月に同じ支払先の明細を2枚作らない」までしか守らない。
> 締め月をまたいで同じ案件を二度拾う、取消して作り直したときに前の明細が残る、といった経路は防げない。
> **明細行を案件番号で一意にすれば、明細が何枚できても同じ案件を二度払えない。** これが二重払いに対する本当の歯止めになる。
> 取消は行を削除せず `voided_at` を埋める（部分一意索引から外れるので作り直せる。監査の記録は残る）。
> 支払明細を取り消す関数は、見出しの `status='cancelled'` と明細の `voided_at` を**必ず同じ処理の中で**更新する。

- 二重払いは**明細行の案件番号**で止める（上の `payout_statement_lines_once`）。見出し側の索引だけでは締め月をまたいだ重複を防げない。
- 確定関数 `fix_payouts(month)` の手順（モックの `payoutRows` と同じ）：
  1. 施工代理店ごと：`contractor_id = c` の完了案件 → `contractor_share` の合計。
     加えて `shop_self_of = c and contractor_id <> c` の案件（自社窓口で取次・他社施工）→ `shop_share` を加算（`referred`）。
     現金案件は `cash_kept`／`cash_remit` を分けて集計。
  2. 取次店ごと（`self_of_contractor_id is null` の窓口のみ）：`shop_id_snapshot = s` の完了案件 → `shop_share` の合計。
  3. `transfer_amount` は第5.5節の規則で決める。
  4. 金額0の行は作らない。
  5. 明細行の `description` に案件の説明（完了日・車種・区分・金額）を写す。施工代理店は他社が施工した案件を読めないため、
     明細だけで支払根拠が分かる必要がある（第11.2節）。

### 5.4 現金案件の精算

| 誰から誰へ | 何を | 手段 | 記録先 |
|---|---|---|---|
| 施工代理店 → 本部 | 現金案件の売上 × 20%（本部10%＋取次10%） | 本部→施工代理店の請求書（種別 `cash_collection`） | `invoices` 第6章。入金で `service_orders.cash_remitted_at` 相当は請求書側の `paid_at` で判定 |
| 本部 → 取次店 | 10% | 通常の月次振込 | `payout_statements(payee_type='shop')` に含める（決済手段を問わない） |
| 本部 → 施工代理店 | 80% | **振り込まない**（手元に残す） | `cash_kept_amount` に記録し `transfer_amount` から除外 |

現金の回収記録は申込単位（`applications.cash_collected_at`）。完了報告のゲートは第3.3節。

### 5.5 相殺の切替（③''。設計の分岐点）

`settings.offset_cash_remit` で切り替える。**テーブル構造はどちらでも同じ。**

| | 相殺しない（仮の設定） | 相殺する |
|---|---|---|
| `transfer_amount` | `share_amount − cash_kept_amount`（カード分の80%＋自社窓口取次分） | `share_amount − cash_kept_amount − cash_remit_amount`。マイナスなら 0 で、差額を請求書に回す |
| 現金回収請求書 | `cash_remit_amount` 全額を請求 | 振込で相殺しきれなかった分だけ請求（振込額が0になった場合のみ発生） |
| `offset_applied` | false | true |

相殺する場合は、請求書の明細に「振込額との相殺 −¥X」の行を追加し、`payout_statements.id` を請求書に参照させる（`invoices.offset_statement_id`）。
どちらの運用でも「請求書」と「支払明細」は別テーブルのまま、精算関数の中でだけ両方を見る。

### 5.6 振込CSV

`payout_statements` の `status='fixed'` かつ `transfer_amount > 0` の行から出力する。列の並び・文字コードは本部から後送のフォーマットで決める（④）。
出力は Express 側の関数で行い、DBには「出力した日時と行数」を `payout_exports` に残す（同じ月を二重に振り込まないための記録）。


### 6.3 状態遷移と編集ロック

```
draft（作成済み） → sent（送付済み） → paid（入金済）
      └────────────→ void（取消。番号は欠番として残す）
```

- `draft` の間だけ明細・送料・備考を編集できる。**`sent_at` が入ったら `invoices`・`invoice_lines` は更新不可**（トリガーで拒否。`status`・`paid_*` の変更は関数経由のみ）。
- 送付時に PDF を生成して Storage に置き、`pdf_storage_path` に記録する（後から明細を見ても同じ内容）。
- `sent` にできるのは本部のみ。`paid` にするには `sent_at` が必須（モックの監査で見つけた「未送付のまま入金済→出荷」の抜け道をDB側でも塞ぐ）。
- `paid` にしたときの副作用（関数 `mark_invoice_paid` の中で実行）：
  - `supply`：`supply_orders.paid_at` を入れる。
  - `franchise_fee`：`contracts.fee_paid_at` を入れる。
  - `cash_collection`：明細の案件に `cash_remitted_at` … は持たず、**請求書の `paid_at` を案件から辿って判定**する（列の二重管理を避ける）。
  - `customer`：同様に請求書側で判定。
- 期日超過は状態にせず、`status='sent' and due_on < 今日` で表示する。

### 6.4 作成関数の要点

- `create_cash_collection_invoice(contractor_id, month)`：対象＝`payout_preview` で `contractor_id` 一致・`payment_method='cash'`。
  明細＝案件1件1行、`unit_price = amount − contractor_share`（＝20%）。相殺ありなら第5.5節の行を追加。
- `create_customer_invoice(corporate_customer_id, month)`：対象＝完了かつ `payment_method='invoice'` かつ申込の法人ID一致。
  明細＝案件1件1行、`unit_price = amount`。`issued_on` = 締め月末、`due_on` = 翌月末（`settings.customer_invoice_due_rule`）。
  宛先は**申込の `bill_to_snapshot`**（月内で複数の申込があれば最新のもの）。
- `create_supply_invoice(supply_order_id)`／`create_franchise_fee_invoice(contract_id)`：第7・8章。
- いずれも `security definer` で本部のみ実行可。同じ対象の `draft/sent/paid` があれば作らず既存を返す。
- **案件側の参照列を埋めるのは作成関数**：`create_cash_collection_invoice` は明細に入れた案件の `cash_collection_invoice_id` を、
  `create_customer_invoice` は `customer_invoice_id` を、同じ処理の中で書く。請求書を `void` にする関数はこれらを `null` に戻す
  （戻さないと、その案件が次の請求書作成の対象から漏れる）。

### 7.3 出荷ゲート（請求書を送付した注文だけ出荷できる）

判定は状態名ではなく **`invoices.sent_at` の有無**。`ship_supply_order(order_id)` 関数の中でチェックする。

```sql
create or replace function ship_supply_order(p_order_id bigint) returns void
language plpgsql security definer set search_path = public as $$
declare o supply_orders%rowtype; inv invoices%rowtype; l record; v_dn bigint; v_stock int;
begin
  if not is_hq() then raise exception 'hq only'; end if;
  select * into o from supply_orders where id = p_order_id for update;
  if o.status <> 'received' then raise exception 'already shipped or cancelled'; end if;
  if o.invoice_id is null then raise exception 'invoice not created'; end if;
  select * into inv from invoices where id = o.invoice_id;
  if inv.sent_at is null then raise exception 'invoice not sent'; end if;
  -- 在庫を引き、入出庫履歴を残す。
  -- 台帳（stock_movements）の増減と残高は必ず一致させる。帳簿在庫が足りないのに現物があって出荷する場合は、
  -- 不足分を「調整」として先に台帳に載せてから出荷を記録する（出荷数を丸めて台帳を狂わせない）。
  for l in select * from supply_order_lines where supply_order_id = o.id loop
    select stock_qty into v_stock from products where id = l.product_id for update;
    if v_stock < l.quantity then
      update products set stock_qty = l.quantity where id = l.product_id;
      insert into stock_movements(product_id, movement_type, quantity, balance_after, supply_order_id, note, actor_user_id)
        values (l.product_id, 'adjust', l.quantity - v_stock, l.quantity, o.id, '出荷時の帳簿不足を調整（要棚卸）', auth.uid());
    end if;
    update products set stock_qty = stock_qty - l.quantity where id = l.product_id returning stock_qty into v_stock;
    insert into stock_movements(product_id, movement_type, quantity, balance_after, supply_order_id, note, actor_user_id)
      values (l.product_id, 'ship', -l.quantity, v_stock, o.id, o.code, auth.uid());
  end loop;
  insert into delivery_notes(code, supply_order_id, issued_on, ship_to_snapshot)
    values (next_code('DN', jst_today(), 3), o.id, jst_today(), inv.bill_to_snapshot) returning id into v_dn;
  update supply_orders set status='shipped', shipped_at=now(), shipped_by=auth.uid(), delivery_note_id=v_dn where id=o.id;
end $$;
```

- 料金表は `settings` ではなく専用の小テーブルにする（改定履歴のため）。

```sql
create table service_prices (
  id          bigint generated always as identity primary key,
  price_kind  text not null check (price_kind in ('kei','standard','onebox','yani_option')),
  amount      integer not null,                  -- 16500 / 19800 / 22000 / 5500（税込）
  valid_from  date not null, valid_to date,
  constraint valid_range check (valid_to is null or valid_to >= valid_from)
);
```

申込受付時に有効な価格を引いて `service_orders.amount` に確定値として書く。

### 9.3 祝日 `holidays`

最短希望日（受付から3営業日後）の計算に使う。モックの `HOLIDAYS` 定数に相当。本部が年ごとに登録する。

```sql
create table holidays (
  holiday_on date primary key,
  name       text not null
);
create or replace function add_business_days(p_from date, p_days int) returns date language plpgsql stable as $$
declare d date := p_from; n int := 0;
begin
  while n < p_days loop
    d := d + 1;
    if extract(isodow from d) < 6 and not exists (select 1 from holidays where holiday_on = d) then n := n + 1; end if;
  end loop;
  return d;
end $$;
```

## 11. 行レベルセキュリティ（RLS）

### 11.1 原則

- **全テーブルで `enable row level security` を有効にする**（Supabase では有効にしないと `anon` キーで全行読める）。
- ブラウザは `anon` キー＋ログイン済みユーザーの JWT で直接 Supabase に読みに行く（一覧・詳細表示）。
  **書き込みは原則サーバー関数（`security definer`）経由**。テーブルへの直接 `insert/update` は、確定値を含まない列に限って許す。
- `service_role` キーは Vercel の環境変数にだけ置き、Webhook 受信（決済結果）とアカウント発行にだけ使う。
- ビューは `security_invoker = on` で作り、元テーブルの RLS を通す。**列を隠す目的でビューを使わない**（元テーブルを直接読めば見える）。
  伏せたい列は別テーブルに分けて、そのテーブルに RLS を書く（第2.6節の口座がその例）。
- **関数を誰の認証情報で呼ぶか**を明確にする。`auth.uid()` で権限を判定する関数（`complete_job`, `ship_supply_order`,
  `mark_cash_collected`, `send_invoice` …）は、**ブラウザから Supabase の RPC として、ログイン中の利用者の JWT で呼ぶ**。
  Express を経由する場合も利用者の JWT を転送し、`service_role` では呼ばない（利用者が空になり全員拒否される）。
  `service_role` で呼ぶのは利用者が存在しない処理だけ：`confirm_payment`／`fix_fees`（決済代行会社の Webhook）、
  `expire_unpaid_applications`（定期処理）、`submit_application` を `anon` で呼ぶ経路（第3.7節）、アカウント発行。

#### 施工代理店に「自社が開拓した取次店の案件（他社が施工）」を見せない（2026-09-23 利用者確定）

**施工代理店が読めるのは、自社が施工を担当する案件だけ。** 自社が開拓した取次店から入った案件でも、
他社の施工代理店が施工したものは件数・金額とも見せない。**その取次手数料の管理責任は本部だけにある**ため。

- 開拓した取次店そのもの（`agency_shops`）は引き続き読める。開拓・登録・QR発行は施工代理店の仕事なので変えない。
- 自社取次窓口で受けた申込は、受付時に自動で自社へ割り当てるので `contractor_id = 自社` となり、この条件で読める。
- 結果として、列単位の制御（個人情報だけ伏せるビュー）は不要になった。`applications_referred` は廃止する。

**画面への影響**：モックの施工代理店ダッシュボードのカード「自社取次店からの取次」と、取次店管理の「取次数」列は、
他社が施工した案件を数えているため**本番では出さない**。取次店の稼働状況を見せたくなった場合は、
本部が集計した数値だけを返す関数を別に用意する（行は読ませない）。

**支払明細だけは例外的に金額が出る**：自社取次窓口で取り次ぎ、他社が施工した案件（`line_kind = 'referred'`）は
取次分10%がその施工代理店に支払われる。この場合でも案件そのものは読ませず、`payout_statement_lines.description`
に説明文を写しておくことで、明細だけで支払根拠が分かるようにする（第5.3節）。
**この10%を今後も施工代理店に支払うかは、本部が検討中の報酬体系しだいで変わりうる**（下記）。

> **未確定：施工代理店への報酬体系**（2026-09-23 利用者より）
> 本部は、施工代理店が取次店を開拓したことに対する報酬を、現行の配分とは別の形で検討している。
> 決まれば配分ルールそのものが変わる可能性があるが、**第1.3節の「確定値の書き込み」により過去の確定済み月は影響を受けない**。
> 新しい報酬が案件単位でないなら（月額・件数段階など）、`payout_statements` に種別を足すか、報酬専用のテーブルを別に作る。

### 11.4 ポリシーの書き方（代表例）

```sql
alter table service_orders enable row level security;

-- 読み取り：本部は全行。施工代理店は自社が施工担当の案件。取次店は自店経由の案件。
-- 判定関数は (select …) で包む。包まないと行ごとに評価され、件数が増えたとき一覧が重くなる。
create policy service_orders_select on service_orders for select using (
  (select is_hq())
  or contractor_id = (select my_contractor_id())
  or exists (select 1 from applications a
              where a.id = service_orders.application_id and a.shop_id = (select my_shop_id()))
);

-- 書き込み：直接の update は本部にも許さない（すべて関数経由）。
-- ポリシーを作らなければ insert/update/delete は誰もできない（security definer 関数は RLS を通らない）。
```

```sql
alter table applications enable row level security;
-- 施工代理店は「自社が施工を担当する申込」だけ。自社が開拓した取次店の案件でも、
-- 他社が施工したものは読めない（手数料の管理責任は本部のみ）。
-- 施工代理店の判定は申込側の contractor_id ではなく「配下の案件」で行う。
-- 複数台の申込で1台が完了した後に残りを差し戻すと申込側の contractor_id は空になるが、
-- 完了した車の顧客情報・現金回収の記録は施工した会社が引き続き読めなければならないため。
create policy applications_select on applications for select using (
  (select is_hq())
  or shop_id = (select my_shop_id())
  or exists (select 1 from service_orders so
              where so.application_id = applications.id and so.contractor_id = (select my_contractor_id()))
);
```

```sql
alter table pre_check_signatures enable row level security;
create policy pre_check_select on pre_check_signatures for select using (
  is_hq() or contractor_id = my_contractor_id());
-- insert は関数経由のみ。update/delete のポリシーは作らない（誰も変更・削除できない）
```

```sql
-- 確定値の列を守る：関数以外からの更新を拒否するトリガー
create or replace function guard_fixed_columns() returns trigger language plpgsql as $$
begin
  if old.shares_fixed_at is not null and (
       new.fee_amount is distinct from old.fee_amount or new.hq_share is distinct from old.hq_share or
       new.shop_share is distinct from old.shop_share or new.contractor_share is distinct from old.contractor_share or
       new.amount is distinct from old.amount or new.self_served is distinct from old.self_served or
       new.contractor_id is distinct from old.contractor_id or new.completed_on is distinct from old.completed_on)
  then raise exception 'fixed shares cannot be changed'; end if;
  if old.status = 'completed' and new.status <> 'completed' then raise exception 'completed job cannot be reopened'; end if;
  return new;
end $$;
create trigger service_orders_guard before update on service_orders for each row execute function guard_fixed_columns();
```

| `session{role,entityId}` | `user_profiles` ＋ Supabase Auth | ロール選択ログインは廃止 |
